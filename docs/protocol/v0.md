# Smart Neckband V0 Protocol

The V0 packet format is transport independent. UART, Bluetooth Classic SPP, and BLE GATT send the same bytes. The realtime stream is binary only; JSON and CSV are not used as realtime wire formats.

All integer fields are little-endian. CRC is CRC-16/CCITT-FALSE over the header and payload, excluding the trailing CRC field.

## Packet Rates

| Packet | Type | Payload bytes | Packet bytes | Nominal rate |
|---|---:|---:|---:|---:|
| `ECG_BATCH` | `1` | 48 | 68 | 25 packets/s |
| `IMU_BATCH` | `2` | 32 | 52 | 25 packets/s |
| `DEVICE_STATUS` | `3` | 32 | 52 | 1 packet/s |
| `VOICE_TEXT_CHUNK` | `4` | 48 | 68 | On final ASR text; retransmitted until ACK |
| `VOICE_STATUS` | `5` | 20 | 40 | 1 packet/s while Voice is enabled |
| `VOICE_TEXT_ACK` | `6` | 8 | 28 | PC-to-device after durable SQLite insert |

## Header

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| magic | `uint16_t` | 2 | `0x4E53`, wire bytes `53 4E` |
| protocol_version | `uint8_t` | 1 | `1` |
| packet_type | `uint8_t` | 1 | `1` through `6` |
| payload_length | `uint16_t` | 2 | Payload length only |
| packet_sequence | `uint32_t` | 4 | Monotonic packet sequence across all packet types |
| timestamp_us | `uint64_t` | 8 | Monotonic device timestamp; batch packets use the first sample timestamp |

Header size: 18 bytes.

## ECG_BATCH Payload

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| first_sample_index | `uint32_t` | 4 | Index of the first ECG sample in this packet |
| sample_rate_hz | `uint16_t` | 2 | `500` |
| sample_count | `uint8_t` | 1 | `20` |
| flags | `uint8_t` | 1 | Bit flags below |
| samples | `uint16_t[20]` | 40 | Raw ADC counts, unfiltered |

ECG primary data is raw ADC counts. Firmware must not filter, smooth, discard, or replace this stream with derived HR or R peaks.

## IMU_BATCH Payload

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| first_sample_index | `uint32_t` | 4 | Index of the first IMU sample in this packet |
| sample_rate_hz | `uint16_t` | 2 | `50` |
| sample_count | `uint8_t` | 1 | `2` |
| flags | `uint8_t` | 1 | Bit flags below |
| samples | `imu_point[2]` | 24 | Raw MPU6050 accel and gyro values |

Each `imu_point` is six signed 16-bit fields in this order: `ax`, `ay`, `az`, `gx`, `gy`, `gz`.

## VOICE_TEXT_CHUNK Payload

`VOICE_TEXT_CHUNK` carries only a non-empty final ASR result. Partial ASR
results and microphone audio are never sent over BLE.

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| utterance_id | `uint64_t` | 8 | Random per utterance; reused for retransmission |
| chunk_index | `uint8_t` | 1 | Zero-based |
| chunk_count | `uint8_t` | 1 | `1..15` for the 512-byte limit |
| text_length | `uint8_t` | 1 | Used bytes in `text`, `1..36` |
| flags | `uint8_t` | 1 | Bit 0 `FINAL`, bit 1 `RETRANSMIT` |
| text | `uint8_t[36]` | 36 | UTF-8 bytes followed by zero padding |

Chunk boundaries are byte boundaries and may split a multi-byte UTF-8 code
point. The PC concatenates all chunks in index order and decodes UTF-8 only
after the complete message is present. The complete text is limited to 512
bytes.

The device retains at most four final texts in RAM. It sends text through a
separate low-priority BLE queue, one chunk at a time, so voice traffic cannot
evict ECG packets. A complete text cycle is retransmitted every two seconds
until ACK. Pending text does not survive a reboot.

## VOICE_STATUS Payload

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| state | `uint8_t` | 1 | Voice runtime state below |
| flags | `uint8_t` | 1 | Runtime-specific connection/activity flags |
| last_error | `uint16_t` | 2 | Stable voice error code, zero for none |
| wake_count | `uint32_t` | 4 | Accepted offline wake events |
| asr_success_count | `uint32_t` | 4 | Non-empty final results |
| asr_error_count | `uint32_t` | 4 | Failed/aborted ASR sessions |
| text_drop_count | `uint32_t` | 4 | Final texts rejected because the RAM queue was full |

Voice state values are: `0 DISABLED`, `1 IDLE_WAKE`, `2 ASR_CONNECTING`,
`3 STREAMING`, `4 WAIT_FINAL`, and `5 ERROR_COOLDOWN`.

Voice flag bits are: bit 0 `AUDIO_READY`, bit 1 `EXACT_MODEL_READY`, bit 2
`WIFI_READY`, and bit 3 `ASR_WEBSOCKET_CONNECTED`. Stable `last_error`
values 1 through 10 represent configuration, exact model, audio, Wi-Fi,
WebSocket, provider protocol, audio queue overflow, final timeout, empty
final, and pending-text queue failures respectively.

## VOICE_TEXT_ACK Payload

| Field | Type | Bytes | Notes |
|---|---:|---:|---|
| utterance_id | `uint64_t` | 8 | Final text durably accepted by the PC |

The PC writes this packet to the BLE RX characteristic only after SQLite has
successfully inserted or deduplicated the stable instruction
`voice-<utterance_id as 16 lowercase hex digits>`. An ID/text conflict,
invalid UTF-8, missing chunk, or persistence failure is not ACKed and is not
forwarded to the Agent Webhook.

## BLE GATT Transport

The ESP32-C3 profile uses the ESP-IDF BLE UART service with these UUIDs:

| Role | UUID |
|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| PC-to-device write (RX) | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |
| Device-to-PC notify (TX) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

V0 does not add a second application fragmentation header. The BLE UART component slices the byte stream to the negotiated ATT payload size, and the PC feeds notification chunks into the same incremental `PacketParser` used by serial transport. A notification boundary is therefore not a packet boundary: one V0 packet may span notifications, and one parser input sequence may contain multiple packets. Magic, payload length, packet sequence, and CRC provide resynchronization and integrity checks.

The RX characteristic accepts the encrypted `VOICE_TEXT_ACK` packet. The
device treats RX writes as an arbitrary byte stream and validates magic,
declared length, packet type, and CRC before removing a pending text.

The current ESP32-C3 bring-up profile uses LE Secure Connections Just Works with bonding. The PC application initiates pairing on its first connection, Windows stores the bond, and later connections reuse it without a numeric passkey. The RX characteristic and TX CCCD require link encryption (`ENC`) but do not require MITM authentication (`AUTHEN`), because a headless Just Works exchange intentionally produces `authenticated=0`. GATT traffic therefore remains encrypted, but the initial exchange does not provide MITM verification. A later hardware revision may restore authenticated pairing by showing a dynamic passkey on a trusted display.

## Golden Vectors

The shared vectors live in `docs/protocol/v0_golden_vectors.json`.

The C firmware self-test and Python pytest suite verify the same ECG, IMU,
device-status, voice-text, voice-status, and ACK packets. A protocol change is
not complete until those vectors are updated together.
